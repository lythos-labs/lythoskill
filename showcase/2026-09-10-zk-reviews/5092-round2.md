## Q2 — The `140` provenance gap: does it need to become re-derivable?

**My call: yes, it should become re-derivable — and it is LOW priority, not a blocker.**

First, the measurement itself. I re-derived it rather than assuming:

```
$ bun -e '…const rows = m.CLI_LAYOUTS.map(a => ({id:a.id, n:a.perRoleScoping.length}))…'
MAX = 140 {"id":"dsh","n":140}
top5: dsh 140, kiro 87, opencode 54, claude-code 47, goose 39
MAX const = 200
```

So the comment's claim ("当前最长 140") is **currently true**, with a single row at the bound's
70%. What is missing is exactly what the coordinator said: not the value, the **carrier**. Nobody can
recompute 140 from the repo without re-running my one-liner, and nobody would know to.

**Why it should be closed.** Three reasons, in order of weight:

1. **This card is the least able to carry an unattributable number.** Its own thesis — B5 (counts
   must be pinned), B13 (a schema bound needs a stated derivation), B16 (evidence hygiene),
   `ADR-20260910113730375` (claims must be commit-pinned), and now its own round-2 fix — is that a
   number without a carrier is a liability. `AGENTS.md` §2 rule 11 says a factual assertion in a
   comment without something that actually runs behind it is "an unsourced rule wearing a citation".
   The card has now applied that standard to its AC and to its showcase count; leaving a third
   instance inside `cli-layout.ts` is the sweep stopping one file short.
2. **Re-measuring and writing "140" would reset the same trap**, at the next row addition. The only
   durable closure makes it *recomputable*.
3. **The closure is cheap and is the card's own preferred move.** The test at `cli-layout.test.ts:52-57`
   already iterates all 16 rows asserting `length <= PER_ROLE_SCOPING_MAX`. Adding one assertion that
   relates the bound to the observed max turns a literal into an invariant — which is precisely what
   the card did for B2 when it replaced `toEqual(['.goose/skills'])` with "a data-loss hazard must
   cover every *exclusive* fan-out target of its own layout", and explicitly argued the invariant was
   the stronger form. One line, in a test that already exists, over data it already touches.

**The strongest objection, and why I don't think it lands.** The card's own B21 rejected
`expect(patterns.length).toBe(3)` as "钉的是形状不是行为" — pinning shape, not behaviour. Is a
bound-vs-observed-max assertion the same mistake? I don't think so, and the distinction is the one the
card itself drew: a *pattern count* goes red when a legitimate fourth pattern is added (no real
failure) and stays green through the actual failure mode it was supposed to catch. A *bound stands in
a fixed relation to the observed max* assertion goes red exactly when the guard stops guarding a row
that exists — a real failure — and cannot go red for a benign reason. It is the B2 distinction, not
the B21 one.

**If they'd rather not add an assertion**, there is an equally legitimate closure: restate the comment
as a **choice** rather than a **measurement** ("one line of prose; 200 leaves room for growth").
That satisfies no-source-no-rule by not dressing a choice as a measurement — the rule forbids
unsourced *claims*, not decisions. I prefer the assertion, because it additionally fails loudly as a
future row approaches the bound, which the current test does not do (a row at 199 passes silently,
and the next at 201 fails with a message that never says why 200).

**Priority: LOW.** Nothing downstream depends on 140 — not the enforcement (200), not any consumer,
not any decision. Applying `zk-review.md`'s own test ("是否导致 executor 无法独立执行?"), no executor
gets stuck or goes the wrong way because this provenance is absent. A reader is mildly misled into
treating 140 as verified; that is a bookkeeping defect, not a blocker. It should ride in whatever
batch next touches `cli-layout.test.ts`.
