# 哲學

> 為什麼宣告式治理存在，以及為什麼「再裝一個技能就好」這條路已經走不通了。

## 治理問題

你的 `~/.agents/skills/` 會變成垃圾場。它是漸進發生的：

1. 你從 GitHub 裝一個技能——複製到你的技能目錄
2. 你試了 Superpowers，又試了 skill-manager——各自留下自己的 symlink
3. 你為不同專案測試技能——舊版本、壞連結、默默衝突
4. 你的 agent 看到你裝過的所有東西。哪些技能*應該*是 active 的？沒人知道。

**你的技能目錄變成 config 中最髒的目錄。** Agent 看到的是歷史債務，不是策展過的工具箱。

### 為什麼會這樣

兩個截然不同的需求被塞進同一個目錄：

1. **儲存**——一個放所有你可能會用的技能的地方，跨所有專案
2. **選擇**——*這個*專案現在應該 active 的特定技能集合

當 `~/.agents/skills/` 同時承擔兩個角色時，你收集過的每一個技能都對每個 agent session 可見。更多技能在目錄裡意味著更多 context 被消耗、更多 trigger 衝突、更多不可預測的行為。

### 解法：把儲存跟選擇分開

Lythoskill 引入兩個本來就該分開的概念：

- **冷池**——技能住的地方。一個放 git clone 技能 repo 的目錄。把所有東西放在這裡。冷池裡的東西不會自動 active。
- **工作集**——agent 看到的東西。`.agents/skills/` 中的 symlink 農場。只有牌組宣告的技能才會出現在這裡。

作者截至 2026-05-20 的實際數字：冷池中有 **74 個 repo 共 871 個技能**——所有曾經收集的。但任何專案的工作集只有 **13 個技能**——與 `skill-deck.toml` 宣告的完全一致，不多不少。

儲存一切，只啟動你需要的。

這不是工具層面的失敗，是**治理層面的失敗**。工具修不了這個問題，因為病灶在模式本身：指令式安裝（「把這個技能加進來」）缺乏宣告式對帳（「這些技能，而且只有這些」）。

## 聰明的 Agent，笨的工具

lythoskill 的基礎分層：

```
┌─────────────────────────────────────────┐
│  Agent（智慧層）                         │
│  · 決定何時觸發什麼                      │
│  · 處理模糊                              │
│  · 從錯誤中恢復                          │
│  · 使用對話脈絡                          │
└────────────┬────────────────────────────┘
             │ 結構化輸入 / 明確指令
┌────────────▼────────────────────────────┐
│  CLI（工具層）——純函數                   │
│  · 決定性輸入 → 輸出                     │
│  · 無 LLM API 呼叫                      │
│  · 無 parser / 狀態機 / 分支             │
│  · 無保留狀態                            │
└─────────────────────────────────────────┘
```

**智慧放在 SKILL.md 裡。** CLI 是機械膠水——掃描、連結、查詢。每當 CLI 長出 parser 或狀態機，就是在重複 agent 已經做得更好的事（agent 擁有完整脈絡）。

這就是 lythoskill 套件之所以薄的理由：`packages/lythoskill-deck/skill/SKILL.md` 承載智慧，`packages/lythoskill-deck/src/` 承載穩定的整合程式碼，CLI 把兩者接在一起。三層，各一個責任。

## 薄模式

每個 lythoskill 能力都遵循相同結構：

| 層 | 位置 | 做什麼 |
|-------|-------|------|
| 智慧層 | `SKILL.md` | Agent 面向的指令、決策規則、工作流 |
| 整合層 | `src/`（npm 套件） | 穩定程式碼——SQLite、檔案系統、git 操作 |
| 膠水層 | `cli.ts` | 機械分派——解析參數 → 呼叫整合 → 格式化輸出 |

薄模式是**遞迴的**。Deck、arena、curator、coach——每個都是一個治理其他技能的薄技能。專案本身也是一層薄皮，包裹在成熟基礎設施（git、npm、SQLite、GitHub API）之上。

## 宣告式 > 指令式

```
# 指令式（舊做法）
cp -R cool-skill/ ~/.agents/skills/     # 安裝
rm -rf ~/.agents/skills/cool-skill/     # 解除安裝（也許）

# 宣告式（lythoskill）
# 1. 在 skill-deck.toml 加一行
# 2. 執行 `deck link`
# 3. 工作集與宣告完全吻合
```

**預設拒絕。** 不在牌組裡的技能，物理上不存在於工作集中。不會默默累積。不會有「我忘了裝過那個」。

這和 Kubernetes 從指令式 `kubectl run` 轉向宣告式 YAML 對帳是同一個洞見。期望狀態是真相來源；控制器讓現實與之吻合。

## 玩家與牌組分離

TCG（集換式卡牌遊戲）的類比不是裝飾——是結構性的。它捕捉了一個經過數次迭代才浮現的設計決策：玩家（agent 平台）和牌組（技能集合）是獨立變數。

```
玩家（誰在玩）                    牌組（你用什麼玩）
├─ 平台: claude-code             ├─ max_cards
├─ 模型: claude-opus-4-6         ├─ skills[]
├─ 並行數: 4 agents              └─ combos[]
├─ 工具集
└─ 原生能力
```

**同一副牌組，不同玩家，不同結果。** 同樣的 deck 交給 Claude Code、Kimi 或 Codex，表現不同——不是牌組有問題，而是玩家各有強項。這是特性，不是 bug：它意味著 deck 編碼可重用的知識，而玩家提供執行脈絡。Arena 存在的目的，就是用實證方法量測這個差異。

分離使**組合式重用**成為可能：3 個玩家 + 3 副牌組 = 從 6 個檔案產出 9 種測試配置，而非 9 個手動維護的組合。這和套件管理器比 vendor dependency 更有價值的原理相同——把可重用的產出物和執行環境分開。
