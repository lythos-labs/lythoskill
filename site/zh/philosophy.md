# 哲學

> 為什麼宣告式治理存在，以及為什麼「再裝一個技能就好」這條路已經走不通了。

## 治理問題

你的 `~/.claude/skills/` 會變成垃圾場。它是漸進發生的：

1. 你從 GitHub 裝一個技能——`cp -R` 到工作集
2. 你試了 Superpowers，又試了 skill-manager——各自留下自己的 symlink
3. 你為不同專案測試技能——舊版本、壞連結、默默衝突
4. Agent 看到一個臃腫的工作集。哪些技能*應該*是 active 的？沒人知道。

**工作整合為你 config 中最髒的目錄。** Agent 看到的是歷史債務，不是策展過的牌組。

作者冷池截至 2026-05-20 的實際數字：**74 個 repo 共 871 個技能**。冷池大小因人而異——你的會不同。重點不是數字，而是：沒有治理的狀況下，其中任何一個都可能默默進入你的工作集。使用 lythoskill-deck 之後，專案工作集是 **13 個技能**——與 `skill-deck.toml` 宣告的完全一致，不多不少。

這不是工具層面的失敗，是**治理層面的失敗**。工具修不了這個問題，因為病灶在模式本身：指令式安裝（「把這個技能加進來」）缺乏宣告式對帳（「這些技能，而且只有這些」）。

## 聰明的 Agent，笨的工具

lythoskill 的基礎分層：

```
┌─────────────────────────────────────────┐
│  Agent（智慧層）                         │
│  · 決定何時觸發什麼                      │
│  · 處理模糊                              │
│  · 從錯誤中恢復                          │
│  · 使用對話脈絡                          │
└────────────┬────────────────────────────┘
             │ 結構化輸入 / 明確指令
┌────────────▼────────────────────────────┐
│  CLI（工具層）——純函數                   │
│  · 決定性輸入 → 輸出                     │
│  · 無 LLM API 呼叫                      │
│  · 無 parser / 狀態機 / 分支             │
│  · 無保留狀態                            │
└─────────────────────────────────────────┘
```

**智慧放在 SKILL.md 裡。** CLI 是機械膠水——掃描、連結、查詢。每當 CLI 長出 parser 或狀態機，就是在重複 agent 已經做得更好的事（agent 擁有完整脈絡）。

這就是 lythoskill 套件之所以薄的理由：`packages/lythoskill-deck/skill/SKILL.md` 承載智慧，`packages/lythoskill-deck/src/` 承載穩定的整合程式碼，CLI 把兩者接在一起。三層，各一個責任。

## 薄模式

每個 lythoskill 能力都遵循相同結構：

| 層 | 位置 | 做什麼 |
|-------|-------|------|
| 智慧層 | `SKILL.md` | Agent 面向的指令、決策規則、工作流 |
| 整合層 | `src/`（npm 套件） | 穩定程式碼——SQLite、檔案系統、git 操作 |
| 膠水層 | `cli.ts` | 機械分派——解析參數 → 呼叫整合 → 格式化輸出 |

薄模式是**遞迴的**。Deck、arena、curator、coach——每個都是一個治理其他技能的薄技能。專案本身也是一層薄皮，包裹在成熟基礎設施（git、npm、SQLite、GitHub API）之上。

## 宣告式 > 指令式

```
# 指令式（舊做法）
cp -R cool-skill/ ~/.claude/skills/     # 安裝
rm -rf ~/.claude/skills/cool-skill/     # 解除安裝（也許）

# 宣告式（lythoskill）
# 1. 在 skill-deck.toml 加一行
# 2. 執行 `deck link`
# 3. 工作集與宣告完全吻合
```

**預設拒絕。** 不在牌組裡的技能，物理上不存在於工作集中。不會默默累積。不會有「我忘了裝過那個」。

這和 Kubernetes 從指令式 `kubectl run` 轉向宣告式 YAML 對帳是同一個洞見。期望狀態是真相來源；控制器讓現實與之吻合。
