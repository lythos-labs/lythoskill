### Pitfalls

- **npm 首发传播延迟会造成"双重发布"错觉**：第一次 `npm publish` 实际成功，但 `npm view` 立刻 404（传播延迟，同 v0.18.0 事故）；以为失败重发 → E403 "cannot publish over the previously published versions"——**E403 恰恰是首发成功的证据**。验证发布要用精确信号（`[ "$OUT" = "0.19.0" ]`），不能 grep 版本号——404 错误文本里就含着版本号，grep 会假阳性（`|| true` 同类的错误）。
- **sed 重写后必须 restore，且每次 attempt 都要**：第二次（失败的）publish attempt 的 sed 重写没恢复，工作树残留 `^0.19.0`——daily 前 git status 抓到。教训：rewrite/publish/restore 三段必须在一个命令链里原子完成。
- **e2e 断言别对裸 brief**：arena CLI 把 brief 包进 evaluation-cell prompt 模板再传给 adapter，stdout 里是完整模板文本。stub e2e 首跑断言 `STUB-HEADLESS-OUTPUT: e2e stub task` 失败即因此。这是 e2e 相对单测的增量信息。
- **dsh 的 Node 门槛**：README 写 ≥22.19；nvm 有 v22.18.0（不够）和 v24.19.0（够）。probe 契约、凭证（`$DSH_HOME/.credentials.yaml`）都验证过。
