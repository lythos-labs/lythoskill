# Week 21, 2026 (May 18 -- May 24)

## TL;DR

W21's center of gravity was the **philosophical crystallization of the orchestrator identity**. The "smart agent, dumb tool" principle converged from three independent streams -- entropy-check boundary (CLI reports facts, agent judges), combo-as-prompt (the combo prompt IS the orchestrator, not another skill), and curator role re-derivation (agent-assisted discovery, not rigid indexer). This unification, expressed across wiki entries, README tagline, and deck SKILL.md, gives the thin-skill architecture its philosophical anchor: orchestration logic sinks by weight, and the orchestrator is distributed across the three layers, not centralized.

In parallel, the project's **public face went from README to deployed VitePress site in 3 days** -- pattern inventory (May 19) to scaffold (May 20) to narrative restructure with EN+ZH i18n and custom theme (May 21). Four iterations of site narrative were needed because the initial approach started from project-internal concepts (cold pool + working set) rather than the user's actual pain (global vs project skills, context window limits). The winning frame: "Deck is a gist for skills."

The single most important decision: **ADR-20260519144445916** locked in that `working_set` must never alias the build output directory. The May 17 rename of the field to `skills` (commit 87937cb) was reverted on May 19 (commit 64d0d41) because `skills/` is the committed build output and `deck link` overwrote it with symlinks. The field name IS `working_set` -- the rename was the aberration.

## Project Lesson Candidates

1. **Agent BDD disproportional return.** Zero-knowledge subagent verifying 3-target POSSE lifecycle found `deck remove` asymmetry (also_link_to targets left stale) in 14 seconds. Unit tests covered `link` fan-out but nobody tested `remove`. Agent BDD tests agent reasoning about multi-command state transitions, not isolated mechanical behavior. The cost per scenario is low; the catch rate is high.

2. **Medium models outperform large for SOP execution.** Haiku ran 3 curator BDD scenarios (14s/114s/42s) -- the fuzzy search scenario found 4 MORE repos than the opus baseline. Well-defined SOPs + medium model = less overthinking = cleaner execution. This validates the memory entry from the same session.

3. **Site narrative: start from user's problem, not our concepts.** The first 3 iterations of the VitePress site narrative failed because they started with "cold pool + working set" -- concepts only meaningful inside the project. The winning iteration (number 4) started from: "You have skills. You want to share them, reuse them, switch between tasks." Strangers do not share our context.

4. **Orchestrator is distributed by weight, not centralized in one component.** External evaluators searching for a single "orchestrator" miss that the orchestration logic is distributed across combo prompt (light), SKILL.md (medium), and CLI (heavy). The weight decides the layer -- a 2-line prompt template doesn't need a CLI wrapper. This is the thin pattern made explicit.

5. **working_set field rename was a dangerous false positive.** The May 17 rename (`working_set` → `skills`) looked like a clean field name improvement but created a collision with the build output directory. `deck link` overwrote committed `skills/` with symlinks. The fix (ADR-20260519144445916 + husky guard) was simple, but the lesson is: field renames that collide with filesystem conventions are not cosmetic -- they are structural hazards. The revert happened within 48 hours, but the W20 weekly already shipped with the claim that the rename was permanent.
