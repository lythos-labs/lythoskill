# SSOT vs copy: dynamic views are queries, templates have one carrier

> Files are truth; views are queries; generated artifacts are projections.
> A copy is none of the three.

## Context

This applies whenever a document is derived from other documents and a reader
needs it to be current:

- "Which daily file is the latest?" (read path)
- "What is the project state?" (`cortex/INDEX.md`)
- "What shape does a task card have?" (`TASK-TEMPLATE.md`)

All three look like places to "just write a small index/template file". All
three fail the same way: the copy is correct on the day it is written and
silently wrong afterwards, because nothing forces it to move when the source
moves.

## Details

### The three roles

| Role | Definition | Example |
|------|------------|---------|
| **SSOT** | The file the write side produces; the only thing allowed to be edited by hand | `daily/YYYY-MM-DD.md`, `cortex/tasks/**/*.md`, `templates/task.md` |
| **Query** | A rule over the SSOT evaluated at read time; no stored result | `cortex list`, `cortex probe`, the latest-daily one-liner |
| **Projection** | A materialized query result, regenerated by the tool that owns it | `cortex/INDEX.md` (by `cortex index`), `skills/**` (by `creator build`) |

A **copy** is a fourth thing and is always a defect: it has the form of a
projection but no generator, so it drifts.

### Rule 1 — Dynamic views are queries

"Latest daily" is a predicate over dated filenames, not a position in a sort:

```bash
ls daily/ 2>/dev/null | grep -E '^[0-9]{4}-[0-9]{2}-[0-9]{2}\.md$' | sort | tail -1
```

Why the filter is not optional:

| Period | Failure |
|--------|---------|
| 2026-04-23 → 05-05 | `daily/README.md` sorted last under every collation; `tail -1` returned it |
| 2026-05-05 → 10-23 | Rename to `_README.md` fixed en_US only; under `LC_ALL=C` `_` sorts after digits → `tail -1` returned `_README.md` |

After the `grep`, sort keys are ASCII digits and `-`, which order identically
under every collation, and non-date members cannot participate.

`cortex/INDEX.md` is the positive example: generated by `cortex index`,
committed as cache, never edited. The same test applies to any proposed
`daily/INDEX.md` — if no command regenerates it, it is a copy.

### Rule 2 — Templates have one executable carrier

A template is a closed set of section names that `probe`, hooks, and reviewers
read. `cortex` shipped four carriers and they drifted (shapes as of 2026-10-23,
before the migration):

| Carrier | Who reads it | Drift |
|---------|--------------|-------|
| `src/lib/template.ts` (hardcoded) | CLI task/ADR creation | `Technical Approach`, `Progress Log`, `Impact` |
| `templates/epic.md` | CLI epic creation | Chinese sections + `lane` frontmatter |
| `assets/*-TEMPLATE.md` | no code; copied by `cortex init` into adopters | `Cross-Package Impact Checklist`, `TDD Cycles`, `Options Considered`, `Consequences` |
| `skill/assets/*-TEMPLATE.md` | agents, via `SKILL.md` ("read the template file") | a third shape; its Status History note still says `仅人工记录，不用于机器解析` although `probe` parses it |

The two shipped copies are the worst shape: one is dead on arrival (nothing
parses it), the other is what the skill tells agents to read, and neither is
validated against what the tool produces. Decision: one artifact per template
under `templates/`; `cortex init` ships the same file; a test pins the rendered
section list against the file (precedent: `status-history.test.ts`
"one shape, no drift"). The CLI-generated section set is canonical; asset-only
sections are retired deliberately, not migrated by accident.

**Current state (migrated 2026-10-23).** The four carriers are now one:
`templates/{task,epic,adr,handoff}.md` are rendered by `src/lib/template.ts`;
`cortex init` copies those same files into the adopter project; `assets/` keeps
only the post-commit hook, and `skill/assets/` no longer exists. Two mechanisms
hold it: `src/lib/template-drift.test.ts` pins each rendered section list to an
explicit spec and fails if any `*-TEMPLATE.md` or `skill/assets/` copy
reappears; the skill's rule is now "cards are generated, never copied" —
`cortex task create "<title>"` output *is* the example.

**This exact drift was already named on 2026-09-11** — Class 1 "Carrier drift"
in `01-patterns/2026-09-11-drift-classes-*` lists the same four carriers. Naming
a drift class did not remove the instance; six weeks later the shapes still
differ, because nothing owned the second carrier. The lesson is Rule 2 itself:
a named drift still needs a mechanism (one carrier, or a pinned copy).

### Rule 3 — Docs reference, they do not inline

A skill or wiki that needs to show a shape links the carrier path or shows a
generated excerpt. Hand-copied template bodies are not a supported carrier —
agents are probabilistic readers after compaction, and a copy degrades silently
while a path degrades into a read.

## When to Apply / When Not to Apply

Apply when a derived artifact is read on every session or gates a write
(handoff lookup, index, template, generated command list).

Do **not** apply when the artifact is a one-time historical record. Dated
dailies, weeklies, ADRs, and `showcase/` artifacts are snapshots; they stay as
written. Do not "fix" old records to match today's convention.

Do **not** command-ize a query whose consumers run where the command is not
installable. Skills ship as text into adopter projects; a `bunx` binary is not
guaranteed there. A correct one-liner beats an unavailable binary. Revisit when
a second consumer needs the result as data.
