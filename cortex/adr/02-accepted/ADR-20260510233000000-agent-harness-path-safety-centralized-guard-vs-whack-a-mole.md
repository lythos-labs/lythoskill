# ADR-20260510233000000: Centralized path-guard vs whack-a-mole for agent-generated path traversal bugs

## Background

2026-05-10 deck QA sweep found 1 P0 + 8 P1 path traversal bugs — all the same root cause: `alias` from deck.toml treated as trusted path component in `join(WORKING_SET, alias)` across 6+ functions. These bugs were naturally generated by agents — the "default" behavior for an LLM writing filesystem code is to trust input.

The question: what's the right fix pattern for agent-generated systemic bugs?

## Options

### Option A: Whack-a-mole (修每个实例)

Fix each occurrence individually in `link.ts`, `remove.ts`, `to-symlink-snapshot.ts`, `add.ts`.

| Pros | Cons |
|---|---|
| Minimal change per file | Same bug will be re-introduced by next agent |
| No new module to maintain | 9 separate fix points to review |
| | No documentation of WHY this is wrong |
| | Agent learns nothing — will repeat |

### Option B: Extract centralized guard (path-guard.ts)

Write a single `validateAlias()` / `safeResolveInDir()` / `validateWorkingSet()` module, apply at all call sites.

| Pros | Cons |
|---|---|
| Single source of truth for path safety | New module to maintain |
| Self-documenting (CWE-22 header) | Requires import at each call site |
| Future agents read the guard → learn the pattern | |
| Easy to add husky check: "does file import path-guard?" | |
| Easy to extend (new sanitizers added in one place) | |

### Option C: Static analysis only (semgrep/codeql rule)

Write a rule that detects unsafe patterns, warn on commit.

| Pros | Cons |
|---|---|
| Zero code changes | Only warns, doesn't fix |
| Language-agnostic pattern | Rules need maintenance as code evolves |
| | Doesn't teach the agent — just blocks |

## Decision

**Option B — centralized guard module.**

Rationale:
1. The guard itself IS documentation. A future agent reading `path-guard.ts` sees CWE-22, allow-list policy, the resolve→realpath→boundary-check pattern.
2. Combined with husky pre-commit check, it prevents re-introduction without depending on external tools (semgrep/codeql not installed everywhere).
3. Pattern scales: next systemic bug class (e.g. shell injection) gets `shell-guard.ts`, same architecture.
4. The alternative (whack-a-mole) already failed — these bugs existed across 6 files precisely because each was fixed independently in the past.

## Implementation

- `packages/lythoskill-deck/src/path-guard.ts` — centralized validation
- `scripts/check-path-safety.ts` — husky pre-commit guard (<100ms)
- `.husky/pre-commit` step 4 — blocks commit if unsafe patterns detected
- Applied to: `add.ts`, `remove.ts`, `to-symlink-snapshot.ts`, `link.ts`

## Consequences

- New deck code that uses `join(WORKING_SET, alias)` without importing `path-guard` will be blocked at pre-commit
- Future systemic bugs should follow the same pattern: centralized guard + husky check + ADR
- This ADR should be referenced when similar bug classes are discovered in other packages
