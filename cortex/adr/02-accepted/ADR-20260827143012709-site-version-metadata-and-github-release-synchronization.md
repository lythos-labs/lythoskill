## Background

The lythoskill monorepo publishes to npm, Git tags, GitHub Releases, and a VitePress-powered GitHub Pages site. By 2026-08-27 these channels had drifted apart:

- npm: `0.17.3` (latest published packages)
- Git tags: `v0.9.18` (7 minor versions behind)
- GitHub Releases: `v0.7.0` (marked Latest, severely outdated)
- GitHub Pages site: no version, commit hash, or "last updated" date visible

This made it impossible for a visitor to know which source version the site represented, and impossible for maintainers to confirm that a release had propagated to all four channels. The drift was compounded by `scripts/publish.sh` handling npm publish only — it did not create tags or releases.

## Decision Drivers

1. **Auditability**: Every release should be verifiable across npm / Git tags / GitHub Releases / site.
2. **External trust**: A visitor should see at a glance that the site is current and tied to a specific commit.
3. **Human-readable freshness**: "Last updated: YYYY-MM-DD" is easier to scan than a commit hash alone.
4. **Historical order constraint**: Past incidents (`daily/2026-07-31.md`) established that npm publish must happen before GitHub push, so external consumers can install before docs point at the new CLI. Tag/release logic must fit that order.
5. **Separation of concerns**: npm auth and GitHub auth are different tokens and failure modes; a failure in one should not leave the other half-published.

## Options

### Option A: VitePress footer with injected version metadata

Build a small `site/scripts/inject-version.ts` that reads root `package.json`, `git rev-parse --short HEAD`, and the current date, then writes `site/.vitepress/version.json`. `site/.vitepress/config.ts` imports the JSON and renders the metadata in `themeConfig.footer.message` for both English and Chinese locales.

**Pros**:
- Non-intrusive; appears on every page without cluttering content.
- Footer supports HTML, so version/commit/date can be clickable links.
- Injection is pure build-time glue; no runtime dependencies.
- Works with both `vitepress dev` and `vitepress build`.

**Cons**:
- Footer is at the bottom of the page — less immediately visible than a top-nav badge.
- Requires updating CI build steps to run the injection script.

### Option B: Top-nav version badge

Add a custom VitePress theme component or use `themeConfig.nav` with a static/generated badge like `v0.17.3`.

**Pros**:
- Most visible location.

**Cons**:
- VitePress default nav does not support dynamic HTML badges without a custom theme component or plugin.
- Custom components increase maintenance surface and risk drift with VitePress upgrades.
- A static badge would stale unless generated by the same injection script; a generated badge in nav config is awkward.

### Option C: Dedicated "Releases" page

Create `site/releases.md` that lists versions manually or fetches from GitHub Releases at build time.

**Pros**:
- Central place for release history.

**Cons**:
- Manual lists rot. Automated fetching adds network dependency and complexity.
- Does not solve the "which version is this site right now" problem on every page.

### Option D: Do not display version metadata

Rely on GitHub Releases / tags alone.

**Pros**:
- Zero code.

**Cons**:
- Fails the auditability and trust drivers outright.
- Does not fix the existing drift.

## Decision

**Choice**: Adopt **Option A** now, with the option to later add a top-nav badge (Option B) if footer visibility proves insufficient. Split tag/release creation into a dedicated `scripts/publish-github-release.sh` that runs after npm publish and after `git push`.

**Rationale**:
- Footer injection is the smallest change that satisfies all four channels (npm version, commit, date, links to release/commit).
- Keeping tag/release in a separate script preserves the historical `npm before github push` order and isolates auth failures.
- A dedicated script can be idempotent (skips existing tags/releases), making it safe to re-run.

## Impact

- Positive:
  - Site footer now shows `v0.17.3 · <short-hash> · Last updated: 2026-08-27` (and Chinese equivalent).
  - `scripts/publish-github-release.sh` gives maintainers a one-command way to sync GitHub tags/releases after npm publish.
  - Release SOP documents the canonical order: test → bump → commit → publish → push → tag/release.
- Negative:
  - CI workflows need to run the injection script before `vitepress build`.
  - Generated `site/.vitepress/version.json` and `site/.vitepress/dist/` must be gitignored.
- Follow-up:
  - Backfill `v0.17.3` tag and GitHub Release for the current npm-published version.
  - Consider a top-nav version badge if user feedback says footer is not visible enough.
