## Background

2026-09-10 复核:`.github/workflows/` 里 `bun-version: latest` 共 **8 处** ——
`test.yml` 5 处、`release.yml` 2 处、`deploy-pages.yml` 1 处。
(辩论 judge 记的是 ×7,漏了 `deploy-pages.yml`;复核时全仓 grep 补上。)

平时这只是一个无害的维护选择。但本项目在此前一周刚立了一条纪律(B11):

> `node:*` 是 **Bun 兼容层**,不是 Node 本身 —— 一切行为假设必须由 **Bun 实测的测试**钉死。

那条纪律一旦成立,"跑在哪个 Bun 上"就从无关细节变成了**证据的一部分**:
同一条 dormancy 测试在 Bun 1.3 与 2.x 下的通过与否可能不同,而 CI 不告诉你是哪个。

于是出现一个与 **ADR-20260910113730375**(claims-not-scores)同形的缺口:
**CI 绿是一个断言,但没有一个版本可以归因。** 我们要求本地测试结论写成
`236 pass / 1 skip / 0 fail / 602 expect @ Bun 1.3.11 / macOS`,却允许 CI 报出
一个不写解释器的绿。两者的严格程度不一致,而不一致的那一侧正好是**唯一被外人看到**的那一侧。

## Decision Drivers

1. **`latest` 让绿不可归因。** 失败会以"上游某天改了"的形式突然出现,不可预算、
   不可二分、不可复现 —— 而那正是 CI 存在的理由。
2. **它让"测试钉住了行为"这句话不完整。** 测试钉住了行为,却没钉住解释器;
   解释器是行为的一部分。
3. **不对称已经存在。** 本地基线早就带版本(`@ Bun 1.3.11/macOS`),CI 不带。
   不是"要不要付这个成本",是"要不要把已有的标准用到 CI 上"。
4. **升级本身是严肃的事,不该作为背景漂移发生。** owner 定调原话:
   **「升级本身就是一个比较严肃的问题。」** `latest` 把升级变成了一件没人决定、
   也没人知道何时发生的事 —— 而这恰恰是重大行为变更最危险的进入方式。
5. **需要一条"何时升"的规矩,否则 pin 会退化成死版本。** 这是选项 B 唯一的真实代价,
   必须在同一个决策里一起解决,不能留给下一个人。

## Options

### Option A — 维持 `latest`
**Pros**:
- 零维护;自动吃到上游补丁与安全修复。

**Cons**:
- CI 绿不可归因于任何版本;与 B11 的"行为假设必须由 Bun 实测钉死"直接张力。
- 升级以**背景漂移**的方式进入:没人决定、没人在场、没人知道是哪天。
  对一份把"记录合规度量 = 发现性"当成立项纪律的仓来说,这是最糟的一种变更方式。

### Option B — pin 到精确版本 + 手动升级窗口(**Selected**)
**Pros**:
- CI 结论可归因:`236 pass … @ Bun 1.3.11 / macOS` 在本地和 CI 是同一句话。
- 升级变成一个**有作者、有 commit、有动机**的事件 —— 可评审、可回滚、可二分。
- 与本地/文档里的基线写法自然对齐,不需要新机制。

**Cons**:
- 需要一条"何时升"的规矩,否则变成无人升的死版本(**已随本决策落地,见 Decision**)。
- 吃不到上游补丁,直到有人主动升级。

### Option C — pin `1.3.x`(major.minor)
**Pros**:
- 吃补丁不吃 breaking;不用每次补丁都动 8 处。

**Cons**:
- **引入一个未证的中间假设**:"1.3.x 内的行为不会变"。这个假设本身没有被任何东西支持,
  而 B11 的整个要点就是"行为假设必须有出处"。
- 把不确定性留在中间:既不能保证可复现,也没换来"升级是显式事件"这个主要收益。

## Decision

**Choice**: **Option B** —— 8 处全部 pin 到精确版本(当前 `1.3.11`,与测试基线同一版本),
升级走显式窗口。

**Rationale**:

**CI 绿是一份断言,断言需要可归因。** 本仓已经接受了这个标准 —— 它要求本地结论写成
`… @ Bun 1.3.11/macOS`,拒绝裸 `213 pass / 0 fail`。同一份标准用在 CI 上就只有一种做法:
让版本成为决定的一部分,而不是每次运行时的随机数。

**"何时升"的规矩(与 pin 同生共死,写进 `AGENTS.md §9`)**:

1. 读 Bun release notes,重点看 `node:*`、test runner、TOML、`fs` 行为的变更。
2. 本地在新版本上跑**全量**两包测试,把新基线**按断言写**:
   `236 pass / 1 skip / 0 fail / 602 expect @ Bun <新版本> / macOS`。
3. **8 处 + `AGENTS.md §9` 里的版本串,在同一个 commit 内一起动**,
   commit message 说明第 1 步查了什么。
4. **不许把升级折进无关改动**:否则一次红色分不清是你的改动还是解释器。

**判据(可 grep,不靠记性)**:`grep -rn "bun-version" .github/workflows/`
→ 恒为 8 处,且值恒等于 `AGENTS.md §9` 里写的那个版本。
每个文件**第一处**上方有注释指向该节(其余 7 处不重复注释 —— 8 份同样的注释是噪音,
而"值必须一致"这条已经由第 3 步的"同一个 commit 内一起动"保证)。

**顺带记账**:`deploy-pages.yml` 用的是 `oven-sh/setup-bun@v1`,另两个文件用 `@v2`。
**不在本决策范围内**(pin 的是解释器不是 action 版本),留给下一位;这里只记下它存在,
以免下次复核时被当成新发现。

## Impact

- **Positive**:
  - CI 结论可归因到解释器;本地复现与 CI 结论是同一句话。
  - 升级从背景漂移变成显式事件(有 commit、有作者、有动机)。
  - 与既有 claims-not-scores 纪律(B11 / ADR-20260910113730375)在同一标准上收敛。
- **Negative**:
  - 需要人主动升级,存在"长期不升"的风险 —— 已由上面的 4 步窗口减轻,
    但**没有自动提醒机制**。接受:自动提醒会退化成噪音,而升级的正确触发是
    "某条测试开始需要新行为"或"上游有影响本仓的修复",这两者都不需要机器提醒。
  - pin 值现在有**两个记录点**(8 处 yaml + `AGENTS.md §9` 一行)。一致性靠
    "必须同一个 commit 内一起动"这条纪律,没有机器检查。**这是刻意的**:
    检查 8 处值是否一致可以机器判定,但它输出的是**覆盖率断言**
    (见 ADR-20260910113534807 的判据)—— 而这里的一致性只值一次 grep。
- **Follow-up**:
  - 8 处 pin + 3 处注释(**已落地**)。
  - `AGENTS.md §9` 新增 "Bun version pin" 小节(**已落地**)。
  - 无 schema / 无测试改动:CI 配置不进测试面,本地测试行为不受影响。
